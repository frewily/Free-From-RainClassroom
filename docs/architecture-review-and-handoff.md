更新时间：2026-10-23。

初次复盘基线：本地 `main`，提交 `995f02ce4f197eab6ffd0c421995a56b4b2228ff`。初次撰写前工作区干净，仅新增本文档，没有修改运行代码、提交或推送。文中路径相对仓库根目录，行号仅适用于该基线；后续改动与验证记录见第 7 节。

## 1. 结论与评价尺度

**以单账号、少量课程的个人自动化工具为尺度，整体架构基本合理；配置管理和故障反馈需要收口，不需要全面重构。**

约 2,000 行运行代码（Python 与 Worker 合计），文件课表与内存状态足够支撑当前规模。

| 使用目标 | 当前判断 |
| --- | --- |
| 个人使用，允许看日志处理故障 | 基本合适 |
| 他人 Fork 后按文档配置 | 可以，但配置耦合和学校适配限制需要说明 |
| 长期无人值守，故障自动发现与恢复 | 仍有短板，不能把工作流存活等同于课堂监听正常 |
| 多用户服务平台 | 不属于当前目标，不按平台标准要求本项目 |

优先修运行风险，其次整理结构。暂不引入微服务、数据库、Redis、消息队列，也不以全面面向对象化或 asyncio 重写作为目标。

## 2. 当前结构与调用链

```text
HFUT 教务课表
  → course-schedule.yml → course_schedule.py → data/course_schedule.json
                                              ├→ course_calendar.py → ICS → 手机日历
                                              ├→ Worker + KV → workflow_dispatch
                                              └→ Python 判断当前监听窗口

python-app.yml → python -u start.py
  → 获取课程 / 检查登录 / 签到 → 启动各课堂监听线程
  → WebSocket 消息与 PPT 处理 → 现有题目处理链路
  └→ 可选 ListeningReport → SMTP 开始、结束邮件与日志附件
```

| 文件或目录 | 职责与判断 |
| --- | --- |
| [start.py](../start.py) | 主流程、监听窗口、周期检查和线程等待；入口比较薄，合理 |
| [function/check_in.py](../function/check_in.py) | 登录状态判断、课程发现和签到；仍保留部分旧入口 |
| [function/listening_socket.py](../function/listening_socket.py) | 连接、重连、消息队列、PPT、题目状态及报告接入；职责偏集中 |
| [function/course_schedule.py](../function/course_schedule.py) | HFUT 登录、验证码、课表解析、缓存及窗口读取；当前规模可接受，多学校扩展时需要明确边界 |
| [function/listen_window.py](../function/listen_window.py)、[course_calendar.py](../function/course_calendar.py) | 时间窗口解析和日历生成；独立纯逻辑较多，适合单元测试 |
| [util/](../util/) | 混合 AI、题库、OCR、邮件与通用工具；名字宽泛，但单纯改名收益不高 |
| [config.py](../config.py)、config.ini | 配置读取、接口常量、共享请求头等混合；需区分个人配置与模板 |
| [cloudflare/](../cloudflare/) | 调度代码、测试、部署示例和说明；边界清楚，但配置仍有硬编码 |
| [data/](../data/)、[tests/](../tests/) | 数据产物与单元测试分开，合理 |
| start_old.py、src/ | 旧入口和教程素材；后者不是程序源码，命名容易误导 |

Worker 调度、Actions 执行的组合适合“不维护常驻服务器”的需求，代价是多平台配置与部署。JSON/ICS 是合理的轻量数据交换方式。

注意：当前 `FILTERED_COURSES` 主要控制哪些课程进入监听，不代表只对名单内课程执行签到；见 `function/check_in.py:103`。后续不得借整理架构静默改变此行为。

## 3. 按优先级处理的问题

以下是待改进项，不表示已经修复。每轮只完成一个可验证的小切片，不同时重写多个子系统。

### P1-A：共享请求头与缺失网络超时（后续进展见第 7 节）

- 事实：`function/listening_socket.py:407` 的 `new_headers = headers` 修改的是共享字典，随后写入课堂认证信息。
- 风险：多课堂线程可能相互覆盖请求头；本轮没有复现真实并发污染。
- 事实：该文件 `:412`、`util/enncy.py:12`、`util/ocr.py:12` 等网络请求没有显式超时。
- 风险：外部服务停滞可能拖住处理线程；邮件收尾限时不能解决业务网络调用停滞。
- 建议：请求级配置独立；为阻塞调用确定合理超时与安全失败路径。不要通过自动重试提交类请求扩大重复操作风险。
- 验收：不同课堂请求不改写全局配置；模拟超时不会无限阻塞；不打印认证值；不改变既有提交语义或新增自动作答能力。

## 4. 已有保护与安全边界

当前邮件实现已具备以下措施，不应把旧版已修问题再次列为当前缺陷：

- 邮件配置不完整时跳过报告；`report_call()` 隔离普通报告异常。
- 每课堂报告沿用到重连之后，开始/结束状态防止同一报告重复通知。
- 单个守护发送线程配合队列，按顺序尝试发送开始和结束邮件。
- 消息处理等待、邮件收尾均有限时；线程启动失败已有保护。
- 日志有条数与字段长度上限，并有脱敏处理。

这仍是尽力通知，不保证真实投递、跨工作流恰好一次通知，或 Actions 强制终止后一定收到结束邮件。

其他边界：

- 不新增或强化评分课堂题目的自动作答、自动提交能力；架构整改只处理稳定性、可维护性与安全边界。
- 不输出 SESSION、AI_KEY、ENNCY_KEY、SMTP 授权码、教务密码、JWT 或完整敏感服务响应。
- `config.ini` 仍受版本控制；需区分示例与个人配置。本轮未读取凭证值，不能据此认定存在有效凭证泄露。
- 公开课表与邮件日志仍是用户数据；应明确公开字段及日志保留范围。
- 源码中存在历史签名资源地址注释，属于清理候选；本文不复制地址。媒体未逐一做视觉隐私审查。
- 提交、推送、Secrets 更改、Cloudflare 部署、真实邮件和真实课堂验证分别确认，不从“代码改进”推断生产操作授权。

### 2026-10-23：P1-B 监听线程终止异常监督

本轮按用户确认的范围处理“监听线程异常退出，主线程却没有发现”，不加入自动重建监听任务。

- 新增轻量的 `function/listener_supervisor.py`：管理监听线程、收集课堂编号与异常类型，并通过共享停止事件唤醒主线程；不保存或打印异常正文、认证值或线程 traceback。
- `start.py` 的手动检查与监听窗口两条入口均接入监督，经课程发现函数传至监听线程启动处。异常退出会打断主线程的五分钟等待，记录安全错误并以退出码 1 结束本次运行；共享停止事件也通知其他已启动的监听任务停止。
- 启动部分线程后又遇到线程启动失败时，已启动线程仍由监督器管理并参与收尾。收尾维持所有监听线程共用的 5 秒等待预算；收尾期间发生的线程异常也会在主流程返回前检查。
- 正常下课、窗口结束、普通断线重连及课程去重沿用原有机制。没有删除 `seen_lesson_ids` 来强行重入，没有重新创建失败课堂的监听线程，不增加重复通知或提交。上一切片的“提交结果未知”处理不变。
- 监督针对终止异常，不把“线程仍存活”视为业务健康的证明。它不能强制中断主线程正在进行的 HTTP 请求，也不覆盖线程存活但无进展、进程被强制终止等情形。
